# v14.15 · SMART LOADING — nothing heavy happens while the world is on screen

Chad, 25 Sep 2026: *"You need to make sure the entire game has very smart
loading so there is no sudden stutters or delays before showing full res
models."*

This file is the build's memory, written BEFORE the code and updated at
every checkpoint, so a lost context can pick it up where it stopped.

## What was true before (read from the code, v14.14)

- `whenWorldReady()` gated ONLY the film path, and waited only for each
  chapter's `ready()` (one or two key models: `hdbReady`, a sergeant) plus
  the hands and the ghost, capped at 12 s. The NO-FILM path — Continue into a
  run, any chapter without an `intro` — revealed the world at once.
- Every other model loaded async over an invisible or primitive stand-in and
  appeared whenever it landed: a POP-IN, in view.
- Parsing (meshopt decode of 8–11 MB files since v14.14), texture upload and
  shader compile all ran on the main thread at whatever moment the bytes
  arrived — mid-play: a STUTTER.
- The equipment figure was prefetched in idle time after play began (parse +
  upload in play: a stutter); an item's model was parsed the first time the
  panel or a splash asked for it (the painted icon, then the model popping in).

## The design

1. **A tracker** (CP1): every model the engine or a chapter parses goes
   through one loader class (`GLTFLoaderMO`), and every GLB fetched through
   `assetBytes`; each load is recorded (key, when it started, when it
   landed, whether the world was already on screen). `__enc.loads()`.
2. **The curtain** (CP2): every way into a chapter — the film, Continue, a
   replay, the card — waits under the black/chapter card until (a) nothing is
   in flight, (b) every program is compiled (`compileAsync`, which covers
   hidden objects), (c) every texture is on the GPU (`initTexture`), (d) the
   equipment figure and any item the chapter asked to warm are parsed and
   drawn once offscreen, and (e) two frames have been drawn under the cover.
   Capped (with the loading word showing) so nothing holds the black forever.
3. **Off the main thread** (CP3): meshopt decode in two Web Workers on the
   hosted build, after a self-test decode proves they work (the single-file
   build's strict CSP forbids the blob: a worker is made from, so it keeps
   the main-thread path — and any failure falls back to it).
4. **Download ahead** (CP3): during play, in idle time and at low priority,
   the NEXT chapter's files and every owned item's model are fetched into the
   browser's HTTP cache (bytes only, never parsed, never held in memory), so
   the next curtain is short. At the title, the chapter Continue would open.

## Three things found on the way

1. **A chapter's build() cannot be read for the items it gives.** Every
   chapter registers a WRAPPER `build(ctx) { const st = build(ctx); … }`, so
   `CH.build.toString()` is the wrapper and the regex over it found nothing —
   the curtain never started the Phiboon's item view, and it parsed 108 s
   into play. A chapter now DECLARES `items: [...]` (ch3, e2c3, e2c5, the
   fixture), and chaptertest fails any literal `kit.give('x')` whose item is
   not declared (proved by removing ch3's and watching it fail).
2. **The worker self-test ran while the page was still starting**, and on a
   busy main thread its answer could not be read inside a six-second
   deadline, so the hosted build fell back to the main thread every time. It
   runs at idle now and has no deadline: until a right answer arrives the
   main thread decodes (safe), and a right answer however late turns the
   workers on.
3. **The probe's wait loops matched their own command line** (`pgrep -f
   dbgload2.mjs` inside a shell whose text contains `dbgload2.mjs`), so they
   never ended. Count the probe's OUTPUT lines instead.
