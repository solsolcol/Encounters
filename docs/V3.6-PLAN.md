# v3.6 — save and resume. Live checkpoint doc.

Chad, 30 Aug 2026: *"user should be able to save and resume, with autosave
enabled by default, and with the option to start new game if needed. the
default should always be dropping back to where you were, but starting a
new game is possible."*

This is the feel decision v3.5 deliberately left open, now made. Update
STATUS as work lands, commit at every checkpoint, resume from this file if
a session dies.

## What "where you were" means, decided

The v3.5 save was a CHECKPOINT at chapter boundaries. Chad's ask is
broader — the player should not lose ground — so autosave now also runs
during play. It still is not a quicksave, and the line is drawn on
purpose:

**Saved:** which chapter, the three stats, the inventory, where you were
standing and which way you faced, and whether the chapter is sealed.

**Not saved, deliberately:** her position and phase, cutscene progress,
every timer, the decision panel, the outcome card. Restoring into the
middle of a cutscene or a half-open decision is the fragile case, and it
buys nothing — so **autosave only ever writes while `state === 'play'`**.
On resume she re-arms from hidden, which is also correct staging: you
come back to the deck, not to the middle of a jump scare.

Still true from v3.5: **if it cannot be JSON, it is not state.**

## The rules the flow has to obey

1. **Continue is the default.** With a save, the big button on the title
   screen reads Continue and that is what a returning player presses.
2. **New game is always reachable**, and it is a secondary action, and it
   ASKS before it wipes. Chad's standing rule is "don't lose anything";
   a mistapped New game losing a run is exactly that, in miniature.
3. **The title screen stays.** It carries the logo, the controls and the
   credits, and skipping straight into the world would be a bigger change
   to the frozen v3.3 feel than Chad asked for. Continue is one press.
4. **Fainting does not become a rewind.** If sanity hits zero, the save
   is rewritten to the START of that chapter — same chapter, fresh stats,
   no position. Otherwise closing the tab mid-faint and pressing Continue
   would drop you back three seconds before it with two sanity left,
   which is both a cheat and a trap.
5. **A save that names a chapter this build no longer has must not brick
   the boot.** Same rule as `?ch=` in v3.4: unknown key, fall back, never
   a dead screen.

## What has to become mutable, and how

Resume can land in a different chapter than the one that booted, so the
engine can no longer treat "the chapter" as fixed. It was, everywhere:

| was | becomes |
|---|---|
| `const CH`, `const CH_KEY` | `let` — reassigned by `setChapter()` |
| `const SHRINE`, `GHOST_HOME`, `BOUNDS`, `SPAWN` | still `const` bindings, **mutated in place** |
| `const CINE_SCENES` | gone — `playCine` reads `CH.scenes` |

The mutate-in-place half matters: `const OFFER_POS = SHRINE` aliases that
same Vector3, and several closures captured `BOUNDS`. Reassigning the
bindings would leave every alias pointing at the old chapter's numbers —
a bug that would only show as the player walking through a wall in
chapter 2. Mutating the objects keeps every alias correct by
construction.

`setChapter(key)` is then: swap CH/CH_KEY, mutate the derived values,
`rebuildStage()`, re-apply the chapter's words. It is also the chapter
ADVANCE path, which is why this is the last piece of the multi-chapter
foundation rather than a detour.

## Edge cases found while building it, and closed

Three the first pass got wrong, all found by asking "what does this do when
it is not the happy path":

1. **An explicit `?ch=` link outranks the save.** Otherwise asking for a
   chapter by name resumes you into a different one — and worse, a harness
   inherits whatever run that browser profile was holding. The save is
   HIDDEN in that case, never cleared: opening a deep link must not delete
   a real run behind the player's back, because no confirm appeared and
   nobody asked for it. (`newGame(false)` is the one path that does not
   wipe.)
2. **Continue on a finished game is a replay, not a resume.** With no next
   chapter, `finish()` writes `done: true`, and Continue then resets the
   stats to the chapter's starting values instead of carrying the finished
   run's numbers into a replay. When a next chapter DOES exist the save has
   already moved to it, `done` stays false, and the stats travel with the
   player, which is correct.
3. **The sealed card's Continue and the save must not disagree.**
   `finish()` records the next chapter, so the button advances to it too.
   Inert today — ch1 is the only real chapter — but wiring it now is what
   stops the two drifting apart.

## Save shape (v2)

```
{ v: 2, ch: 'ch1', stats: {...}, inv: {...},
  at: { x, y, z, ry } | null,     // null = start of the chapter
  done: false,                     // chapter sealed, waiting to advance
  t: <epoch ms> }
```

v1 saves (v3.5, live for a matter of hours) still load: they simply have
no `at` and no `done`, which reads as "start of that chapter".

## What is deliberately NOT in this release

- **Multiple save slots.** The linear spine is the simplification; one
  autosave is the whole point. (SCALING-FOUNDATION.md "Do NOT build".)
- **A manual Save button.** Autosave is on by default and always; a save
  button implies it sometimes is not.
- **Skipping the title screen on resume.** See rule 3.
