# V28.0 · THE ENGINE, SURVEYED FOR A THIRD-PERSON TWO-CHARACTER MODE

20 Nov 2026. Read-only survey for the design of episode 4 chapter 5's tag-team segment (docs/V28.0-E4C5-PLAN.md, his
R3, line 53: "toggle between master zavier and grandmaster pho in a tag team like battle , like final fantasy"). Nothing
in the game was changed to write this; the only file made is this one.

**What the line numbers mean.** Commit `de8a6d2`, build.py `VERSION = "27.0"` (build.py 19). `main.js N` is
`src/main.js` line N (18,997 lines). `e4c4.js N` is `src/chapters/e4/e4c4.js` line N (9,130 lines): that file is
GENERATED from `masters/v27.0/parts/*.js` (a_head, b_flat, c_people, c_phofleck, c_props, c_scast, c_story, c_tsound,
c_ufilm, d_play, z_tail), so a part's own lines differ; the task's `c_cast.js` and `c_zfx.js` are chapter 3's parts

`shell.html N`, `fixturetest.mjs N` and the rest are the files at the repo root.

**What was measured, and how.** Section 7's frame counts come from one run of a one-off probe (kept outside the repo)
against `dist/` on a phone-shaped touch context (390 x 844 points, the `LOW` path), counting triangles and draw calls

## 0 · The short answer

1. **`yaw` is the eye and the body at once.** The camera is a grandchild of `yaw` with no offset of its own
   (main.js 931-934), the stick moves `yaw` relative to `yaw.rotation.y` (main.js 18036), and 61 lines of the engine
   plus every chapter read `yaw.position` as "where he is". Nothing anywhere writes `camera.position`. So the cheapest
   correct third person is: **`yaw` stays the ACTIVE hero's pivot, and the camera goes back on a boom** (its own local
   position). Everything that measures a distance stays right by construction; only what reads the LENS as a place
   needs attention (the aim ray, the aim cones, the vision's eye, the torch, the hands' pass, footsteps): section 3.
2. **Chapter 4's fight is not an event.** It is PLAY, with the weapon mode and the chapter's own tick; the event system
   only shows its brief (`kind: 'guard'`, which resolves the moment START is pressed: main.js 5662). Its progress is
   not saved: a Continue restarts it from the brief (section 9).
3. **No phone budget was ever recorded for chapter 4** (its tracker's CP3.7 is unchecked: docs/V27.0-E4C4-BUILD.md
   139). Measured here: its fight hands the GPU 0.64 to 1.40 million triangles and 88 to 112 draw calls a frame with
   about 1.0 GB of pictures; Grandmaster Pho is ONE level only, 168,029 triangles on 231 bones (section 7).

**Recommended shape: a new opt-in seam, built as a declared MODE in the weapon's shape, briefed by an event, entered
and left under a film's black. Not an event kind.** Evidence in section 8.4.

**Biggest risks:** a boom that films, saves and resets do not know about (12.1); the aim ray, the vision's eye and the
hands' pass all standing at the lens (12.2 to 12.4); one-point collision for one body only, and no engine `keepIn`
(12.6); the phone's cost of a second hero on top of a frame that is already large (12.10); one voice at a time under
an 8 dB duck, against "many instructing voice lines" (12.12); a Continue or a replay landing mid-fight (12.8, 12.9).

## 1 · The player rig and the camera

### 1.1 The rig

main.js 929-935:

```js
const CAM_FOV = 72;
const camera = new THREE.PerspectiveCamera(CAM_FOV, innerWidth / innerHeight, 0.08, 160);
const yaw = new THREE.Object3D();      // horizontal rotation
const pitch = new THREE.Object3D();    // vertical rotation
yaw.add(pitch); pitch.add(camera);
yaw.position.set(CH.spawn.x, CH.spawn.y, CH.spawn.z);   // the chapter decides
yaw.rotation.y = Number.isFinite(CH.spawn.rot) ? CH.spawn.rot : 0;
```

- `yaw.position` is the eye's place AND the player's place. `yaw.rotation.y` is his heading, `pitch.rotation.x` his
  nod (positive looks up). `scene.add(yaw)` is main.js 941.
- The lens: 72 degrees VERTICAL, near 0.08 m, far 160 m. On a 390 x 844 phone that is about 37 degrees across; on a
  16:9 desktop about 104.
- **`camera.position` is never written, by the engine or by any chapter** (`grep camera\.position src/` finds no
  write). The only thing written on the camera itself is its roll, `camera.rotation.z` (main.js 2565, 2718, 2727,
  3034, 14676, 15821, 16982, 17160, 17618-17632, 17857), and its lens (`camera.fov`, through `camLens` main.js 15851
  and `kit.lens` main.js 7864).
- Two things hang on the camera: the torch's spotlight and its target (main.js 3672) and the rifle's muzzle flash
  (main.js 4204).
- The hands are a separate scene and camera: `const vmCam = new THREE.PerspectiveCamera(52, innerWidth / innerHeight,
  0.008, 4);` (main.js 8840).
- `ctx.yaw`, `ctx.pitch` and `ctx.camera` are handed to every chapter (`CHCTX`, main.js 8281-8340), and chapters use
  them: a chapter's film places the lens by moving the RIG (e4c4.js 7595-7601):

```js
function camAt(p, q, roll = 0) {
  yaw.position.set(p[0], p[1], p[2]);
  const dx = q[0] - p[0], dy = q[1] - p[1], dz = q[2] - p[2];
  yaw.rotation.y = Math.atan2(-dx, -dz); pitch.rotation.x = Math.atan2(dy, Math.hypot(dx, dz));
  camera.rotation.z = roll;
  stockLod();
}
```

  So in a film "where he is" is wherever the lens is, and the engine puts him back afterwards (`restoreWorld`,
  main.js 15812-15822).

### 1.3 Walking

main.js 18023-18047:

```js
if (state === 'play') {
  let f = 0, s = 0;
  if (keys.KeyW || keys.ArrowUp) f += 1;
  if (keys.KeyS || keys.ArrowDown) f -= 1;
  if (keys.KeyA || keys.ArrowLeft) s -= 1;
  if (keys.KeyD || keys.ArrowRight) s += 1;
  f -= stickVec.y; s += stickVec.x;
  if (kitPose === 'lying' || kitRooted) { f = 0; s = 0; }
  const len = Math.hypot(f, s);
  if (len > 1) { f /= len; s /= len; }
  strafeInput = s;
  const run = keys.ShiftLeft ? 1.75 : 1;
  const speed = 2.55 * run;
  tmp.set(s, 0, -f).applyAxisAngle(new THREE.Vector3(0, 1, 0), yaw.rotation.y);
  vel.lerp(tmp.multiplyScalar(speed), 1 - Math.pow(0.0005, dt));

  const nx = yaw.position.x + vel.x * dt, nz = yaw.position.z + vel.z * dt;
  if (!collide(nx, yaw.position.z)) yaw.position.x = nx;
  if (!collide(yaw.position.x, nz)) yaw.position.z = nz;

  const sp = playerSpeed = Math.hypot(vel.x, vel.z);
  bob += dt * sp * 8.5;
  const gw = kitPose === 'standing' ? smoothK(poseT) : 0;
  yaw.position.y = eyeY + gw * groundFollow(dt) + Math.sin(bob) * 0.028 * Math.min(sp / 2.5, 1);
```

- Keys and the touch stick feed the same two numbers. Movement is RELATIVE TO THE CAMERA'S HEADING, which is exactly
  what a third-person stick wants.
- 2.55 m/s walking; 4.46 m/s with left Shift, a key a phone does not have. The velocity is eased, not snapped, and it
  is a module variable (`vel`): it survives a teleport unless it is zeroed.
- `dt` here is the CLAMPED frame time: `dt = Math.min(clock.getDelta(), 0.05)` (main.js 17960). Under 20 frames a
  second he walks slower than 2.55 m/s. (The standing rule since v7.1 is wall time for every clock in play; the walk
  itself is the old exception and is base-game feel.)
- Each axis is tried on its own, so he slides along a wall.
- `kit.root(true)` holds him still while the look still works (main.js 8104, read at 18030).
- The head bob is written into `yaw.position.y` every frame. In third person that is the pivot bobbing.

### 1.4 Collision

main.js 17913-17934:

```js
const STEP_UP = 0.4;
function groundAt(x, z) {
  const f = stage && stage.groundAt;
  if (typeof f !== 'function') return 0;
  const g = f(x, z);
  return Number.isFinite(g) ? g : 0;
}
function groundFollow(dt) {
  const x = yaw.position.x, z = yaw.position.z, g = groundAt(x, z);
  if (!(Math.hypot(x - groundLX, z - groundLZ) < 1.5)) groundY = g;
  else groundY += (g - groundY) * (1 - Math.exp(-dt * 14));
  groundLX = x; groundLZ = z;
  return groundY;
}
function collide(nx, nz) {
  const g = groundAt(nx, nz);
  if (g - groundAt(yaw.position.x, yaw.position.z) > STEP_UP) return true;
  const p = new THREE.Vector3(nx, 1.0 + g, nz);
  for (const b of BLOCKERS) if (b.containsPoint(p)) return true;
  return nx < BOUNDS.minX || nx > BOUNDS.maxX || nz < BOUNDS.minZ || nz > BOUNDS.maxZ;
}
```

- **One point, 1.0 m above the floor, with no radius.** A blocker is a `THREE.Box3`; the chapter pads its boxes
  instead (chapter 4: 0.14 m, floor to at least 1.40 m: masters/v27.0/parts/d_play.js 59-65).
- **It is the player's own test**: the step rule reads `yaw.position` (main.js 17930). A second body cannot call it.
- `BLOCKERS` is the chapter's own array, `stage.blockers` (main.js 9207, re-pointed on a rebuild at 15727); `BOUNDS`
  is a copy of the chapter's `bounds` (main.js 9203).
- A move of 1.5 m or more in one frame is taken as a teleport and the ground height snaps (main.js 17923).
- **`stage.keepIn` is not read by the engine at all** (`grep keepIn src/main.js` finds nothing of it). Only
  `walktest.mjs` reads it, to prove by flood that the walkable ground stays inside it. What keeps him in a place is the
  blockers and the bounds, nothing else.
- A person can be made solid by a box moved in place inside the blockers array (chapter 4's `castSolid`, e4c4.js
  5947-5951).

### 2.1 What kind of device

main.js 364-370: `HAS_TOUCH` (a coarse pointer, or `ontouchstart`), `IS_PHONE = HAS_TOUCH && Math.max(innerWidth,
innerHeight) < 1100`, `FINE_PTR` (hover and a fine pointer), `LOW = IS_PHONE`. `LOW` is what chapters read to take the

### 2.2 Touch on the canvas (main.js 9346-9418)

All four touch listeners are on the CANVAS only (9414-9418). Anything in the page above the canvas takes its own
touches and the canvas never sees them.

```js

else if (lookId === null) { lookId = t.identifier; ... }
```

- **The move stick**: the first finger that lands in the LEFT 45 % of the screen. It is drawn where the finger lands
  (`#stick`, 112 px, shell.html 2275 and 3355), its throw 52 px (main.js 9377-9380), read as `stickVec`.
- **The look drag**: the first finger anywhere else, 0.0042 radians a pixel (main.js 9382-9383).
- One stick and one look finger at most. There is no pinch, no second look finger, no double tap.
- A TAP is a finger down under 380 ms that moved under 15 px, in play (main.js 9396); it is routed by section 2.4.
- The page refuses the browser's own gestures: `touch-action:none` (shell.html 51), `user-select:none` (56), and the
  long-press menu is refused (the v24.1 rule).

### 2.4 Where a tap goes

`onTouchEnd` (main.js 9389-9413), for a tap in play, tries in this order and stops at the first that takes it
(9400-9402): the chapter's decision object (`stage.pile.hits(x, y) && stage.pile.interact()`), then `hotspotTap(x, y)`
(main.js 3241-3255: a hotspot's own `hits`, or its mark on the screen, `hotMarkHit` 3540), then
`weaponReloadTap(x, y)` (main.js 4855-4862: the chapter's `stage.reloadHits(x, y)`, chapter 4's bowl of water,
e4c4.js 7413). A tap on nothing does nothing. An unlocked mouse click runs the same chain (main.js 9310-9315).

The interact BADGE (`.ibadge` inside `#interact`) and the E key both call `interactNow()` (main.js 3224-3232): the
pile if it is offered, else the nearest live hotspot (`nearestHotspot`, 3111-3148).

### 2.5 Desktop

- **Pointer lock**: `tryLock()` (main.js 9238-9251) only for a fine pointer, never on the title or over the ledger;
  asked for on a canvas click (9318). Locked, the mouse turns him at 0.0022 radians a pixel; with no lock he
  still looks on plain mouse movement (no button held, only in play, 0.0026 a pixel), and a cursor held inside the
  outer 9 % of the window keeps turning him (9321-9344).
- **Mouse** (main.js 9293-9319): nothing while an event is open (`if (ev) return;`, 9303); right button aims (9304);
  a locked left click fires (9306); an unlocked click runs the tap chain; a locked click presses a `pressAim` spot
  (9317).
- **Keys** (main.js 9211-9227): an open event sees the key first and swallows it (`evKey`, 9214). Then F torch (9215),
  V vision (9216), Escape (9218-9221), E interact (9222), Space fire (9223), R reload (9224), Q aim (9225); everything
  else lands in `keys[]` (9226) for the walk: W A S D, the arrows, left Shift. I opens the bag (14283), M the menu
  (14828). Free today: Tab, the digits, C, X, Z, T, G and the rest.

### 2.6 What an open event does to input

Keys go to the event first (9214); the canvas ignores the mouse (9303); hotspots, taps and marks are off (3178, 3242,
3563); the badge is hidden (18105); the bag and the menu refuse (14226, 14390); the whole HUD is hidden by
`body.evopen` (shell.html 219, 223, 246, 332, 380). Every kind but `tap` and `timed` lays a full-screen overlay
(`layout: ... 'full'`, main.js 5577), which is what takes the stick's and the look's fingers away from the canvas
(docs/V7.0-PLAY-KIT.md says so in words). **While an event is open he cannot walk or look by touch.**

### 2.7 How HUD overlap is checked

No harness asserts it. The standing rule (v11.5) is to re-measure every overlap by bounding box on a 390 px phone and
on a desktop whenever a HUD element is added. In practice that is done ad hoc by the drive probes with a small helper
(`box(sel)`: `tools/probes/e4c4drive.mjs` 46-50, `tools/probes/e4c4gold.mjs` 38) and by photographs at 390 x 844 drawn
at two pixels a point. One layout number is hard-coded in the engine: the life bars keep clear of the HUD by fixed
margins (`mx = 74, top = 236, bot = 150`, main.js 7690). A new mode's buttons will need their own measured pass; there
is nothing automatic to lean on.

**(A) `yaw.position` is where he IS** (distances, drains, saves) and **(B) the camera's world placement is where he
LOOKS FROM** (rays, cones, projections, the eye of an effect). Today the two are the same point.

### 3.5 What this adds up to

If `yaw` stays the ACTIVE HERO's pivot (his head, as now) and only the camera moves back along its own local axis:

- **Right by construction**: everything in 3.1, every projection and cull in 3.2, the saves, the sound's distances,
  the chapter's "me". The stick already moves the pivot relative to the camera's heading.
- **To be redirected or switched off in the mode**: the aim ray, cones and the hand's tip (fire from the hero, aim

- **To be added, because nothing has it**: the hero's BODY following the pivot and turning to face his travel (his

  collision; the switch.

The other way round (the camera stays the rig and a body runs ahead of it) makes every line of 3.1 wrong at once.

### 4.3 What a third-person fight could reuse, and what it could not

**Reuse as it stands**

- The whole SHAPE of the fight: a table of numbers, a tick gated on play, seeded streams, waves, `kit.bar` for
  progress, `kit.health` for lives (bars over people, main.js 7653-7700), `kit.lose` for a loss with its own film,
  a film at the end and a phase set before it.
- The brief: a `guard`-style briefed event with START (the standing rule: instructions first, with a START).
- The refusal's words under the reticle (`kit.weaponBlock`), and the rule behind it: a lock always says why.
- `kit.visionStrain`'s ring on a button (main.js 8064, shell.html 3273) as the model for a cooldown ring.
- `ctx.spirit` (main.js 4038-4049) and `ctx.spiritAura` (4052-4069) if the spirits are still seen through the vision.
- Invisible hit proxies (`hitBall`) as what an ability tests against.

**Reuse with a change**

- `stage.shootables()` and `stage.onShot(report)`: sound as a contract, but the ray starts at the lens (4789).
  For a fireball: find the aimed POINT with the lens's ray (or take the nearest spirit inside a cone, which is
  `weaponAssistHit`'s idea and kinder to a touch screen), then fly the ball from the staff to that point.
- `kit.wave` (`kitWave`, main.js 4007-4017; its frame `gwaveFrame`, 4019-4027) is already a golden front of light running out through the world, 24 m in 2.4 s by
  default, colour `0xffc752`. But it spreads from the LENS (vision.js 302), there is one at a time (`gwave` is one
  object, main.js 4004), it needs `vision` declared (4009) and it costs the vision's full-screen pass. As the
  gameplay ring it is the wrong tool unless its eye becomes a parameter; a ring that is a mesh on the floor is one
  draw call and can be tested by the same radius it is drawn at.

**Cannot be reused**

- The weapon's viewmodel, its own hands, the drops from the hand (`ownTipWorld`, 4971-4978), the recoil on the look,
  aim-down-sights: all first person.
- One weapon a chapter, with one FIRE: two heroes with two or three abilities each do not fit `weaponDecl`.
- Nothing in the weapon or in chapter 4 has a cooldown, a second playable body, or a body moved by the stick.

### 6.1 `mkPerson(key, x, z, ry, o)` (1953-2128)

### 6.2 The levels: one skeleton, several skins

`const LEVELS = [['h', 2.2], ['', 7.0], ['m', 14], ['f', Infinity]];` (1754): the suffix added to the key, and the
distance it is drawn out to. So a person `p4amma` is `p4ammah` within 2.2 m (the full body, about 310,000 triangles),
`p4amma` to 7 m (about 41,000), `p4ammam` to 14 m (8,337), and an `f` beyond where a file exists.

- Each further level's skin is bound to the NEAR body's bones (`addLevel`, 2130-2151): one skeleton animates, whichever
  skin is shown. The full body is brought in and out by `fullOn`/`fullOff` (2159-2178).
- The level is chosen each frame by distance FROM THE LENS, scaled by the lens's angle, with 7 % hysteresis:
  `levelFor` 3455, `showLevel` 3460, `peopleLevels(cam = camera)` 3475-3486. A film pins a level (`P.force`); a person
  may scale his own distances (`o.lodK`).
- Only "the people the story turns on" get the `h` level (CLAUDE.md v26.5: a full body costs about 50 MB of a phone's
  graphics memory).

### 6.4 Walking a body along the ground with a gait

Two forms exist, both scripted:

- **In a film**: the walk is a pure function of the film's clock: `pose(P, 'Walking', s / 1.29, true, ...)` at
  0.62 m/s (`walkKneel`, 7690).
- **In play**: chapter 3's Ton leading him to the hall (`src/chapters/e4/e4c3.js` 7244-7272):

```js
if (!Wk.moving) { Wk.moving = true; ... take(P, 'Walking', 0.3); }
const pace = (P.pace && P.pace.Walking) || 1.25, to = TON_WAY[Wk.i], dx = to[0] - g.x, dz = to[1] - g.z, d = Math.hypot(dx, dz);
Wk.v += (pace * (lag < 0.6 ? 1.2 : 1) - Wk.v) * Math.min(1, wdt * 3.5);
const step = Wk.v * wdt;
if (d <= Math.max(step, 0.02)) { g.x = to[0]; g.z = to[1]; Wk.i++; }
else { g.x += dx / d * step; g.z += dz / d * step; P.group.rotation.y += angTo(P.group.rotation.y, Math.atan2(dx, dz)) * Math.min(1, wdt * 5.5); }
g.y += (hallGround(g.x, g.z) - g.y) * Math.min(1, wdt * 9);
P.rate = Math.max(0.5, Math.min(1.35, Wk.v / pace));
```

  That is the whole recipe: a speed eased toward the take's own pace, the body stepped along its heading, the heading
  eased, the floor eased, and **the take's rate tied to the ground covered** (0.5 to 1.35 of its own pace), so feet do
  not slide. It walks waypoints through open ground; it tests no collision.
- The take's own pace and heading are measured when the person is made: the takes that TRAVEL are named by
  `const WALKS = /^(walkdance|Run_02|Run_03|Walking)$/;` (1741); their travel is taken out of the hips and kept
  (`P.travel`, 1983), and `P.pace[name]` and `P.heading[name]` are read from it or from the planted foot (2095-2106).
  **`Running` is not in that list.**
- Chapter 3's children run on paths and give way to him (`kidsTick`, e4c3.js 5286-5318).

## 7 · Rendering

### 7.1 The renderer's settings

- One WebGL renderer, `antialias: true, powerPreference: 'high-performance'` (main.js 686); ACES tone mapping at
  exposure 1.42 (700-701); fog is `FogExp2`; the far plane is 160 m and the sky's dome a 150 m sphere.
- **Pixels** (main.js 674-682):

```js
const PHONE_RATIO = 2;
function pixelRatioFor(ch, low = LOW, dpr = devicePixelRatio) {
  const want = ch && ch.render && ch.render.phoneRatio > 0 ? ch.render.phoneRatio : 0;
  return Math.min(dpr, low ? (want || PHONE_RATIO) : 2);
}
```

  A phone draws two pixels a point unless the chapter asks another number with `render.phoneRatio` (the fixture asks
  1.9 to prove it; chapter 4 asks nothing, so 2). It is applied at boot and on every chapter change (`applyRender`,
  679; `setChapter`, 15759). At 390 x 844 points that is 780 x 1688, 1.32 million pixels a pass.
- **Shadows** (main.js 689-699): `shadowMap.autoUpdate = false`; a shadow map is redrawn only when something asks
  (`shadowDirty`, 18236). `shadowCasterSync` (1820) switches the light's shadow off when nothing casts. **On a phone
  nothing casts**: chapters set `castShadow = !LOW`, and a person's contact shadow is a painted blob (e4c4.js 2116).
  A new light is a cost and a hazard: the count of lights is part of every lit material's shader, so changing it on
  screen compiles shaders on screen (CLAUDE.md v9.4, v15.1; `lightCounts`, main.js 16394).
- `render.freePictures: true` (chapter 4, e4c4.js 164) frees each picture's page-side copy once it is on the GPU
  (`picsFree`, main.js 1486-1525).

### 8.4 Is the tag-team fight an event KIND, a MODE like the weapon, or a new seam?

**Not an event kind.** The evidence:

1. An event takes walking and looking away. Every kind but `tap` and `timed` lays a full-screen overlay
   (main.js 5577) and the whole HUD is hidden by `body.evopen` (5573; shell.html 219, 223, 246, 332, 380); keys are
   swallowed first (9214) and the canvas ignores the mouse (9303). A fight that is walked through cannot live there.
2. A film ends it. `kitFilm` aborts whatever event is open (8012), and opening any event ends the one before (5565).
   A fight that wants a film in its middle (the shockwave's first use, a spirit's entrance) or a brief of its own
   would abort itself.
3. It is saved only as it opened (5590, 11448), for every stat and item at once.
4. The engine's own precedent: chapter 4 needed a walked fight and did NOT make it an event. It added a kind,
   `guard`, whose whole job is the brief, and that resolves the moment START is pressed (5662); the fight is play
   with the weapon mode and the chapter's tick (e4c4.js 6353-6362, 6568-6607).

**Not the weapon mode itself.** It is one weapon with one FIRE, a first-person viewmodel in the hands' pass
(4864-5031), a ray from the lens (4789), recoil written on the look (4598-4622). Two heroes with their own abilities
and cooldowns do not fit `weaponDecl`.

**A new seam, in the weapon's SHAPE.** What the weapon mode shows is how the engine wants a mode built, and each
piece has a line to copy:

- a DECLARATION in the chapter's data, absent in every other chapter, so they are unchanged by construction

- the HUD DERIVED ON THE FRAME into a body class (`weaponPropSync`, 4469-4482; shell.html 331), never switched by
  hand;
- its input bound beside the weapon's (keys 9223-9225; buttons on `pointerdown` in `kitInit`, 7120);
- the chapter told what happened and deciding what it means (`stage.shootables()`, `stage.onShot(report)`: 4790,
  4813): the ENGINE owns the camera, the input, the HUD and the two bodies' movement; the CHAPTER owns the spirits,

- a small validated save field or none (11529, 11555-11558);
- the fixture declaring it with no model, and `fixturetest` proving it on, off, and gone

## 9 · Saves

### 9.1 What a save is

One JSON checkpoint in `localStorage` (`saveCheckpoint`, main.js 11441-11472): `worldState()` (11510-11531: `v`, `ch`,
`stats`, `inv`, `phase`, `conduct`, `choices`, `ward`, `ledger`, `weapon`) plus `at` (the rig's place and heading),
`done` and a time.

```js
if (CH_ASKED) return false;
...
const held = ev && ev.save0 && !(extra && 'at' in extra);      // v24.0 (CP13): a minigame open is saved as it opened
const at = (extra && 'at' in extra) ? extra.at : held ? { ...ev.save0.at } : {
  x: yaw.position.x, y: yaw.position.y, z: yaw.position.z, ry: yaw.rotation.y
};
...
if (at === null) { base.phase = null; base.conduct = { s: 0, a: 0, notes: [] }; }
```

- A `?ch=` session never saves and never reads a save (11446): a deep link cannot test saving.
- A save with no place (`at === null`) is the START of a chapter: no phase, no conduct (11465).
- `applyState` (11532-11579) validates everything it reads; unknown item ids are dropped.

### 9.2 When it is written, and when it is held

```js
const AUTOSAVE_MS = 8000;
function saveHoldOff(ms) { lastSaveAt = Math.max(lastSaveAt, performance.now() - AUTOSAVE_MS + ms); }
function autosave(force) {
  if (state !== 'play' || fainting) return false;
  if (!force && performance.now() - lastSaveAt < AUTOSAVE_MS) return false;
  return saveCheckpoint();
}                                                               // main.js 11499-11508
```

- Every frame asks (18183); a save happens at most every 8 s, **only in play**, never while fainting. So a save can
  land in the middle of a walked fight at any moment.
- Forced: before a film from play (8019), on entering a chapter (16842), on a restart (17889); the decision's opening
  saves (17253).
- Held: for 0.6 s after an event resolves (5830) and after the windows that answer a chapter; and while an event is
  open the save is the run as it stood when the event opened (11448).
- `lose()` rewrites the save to the START of the chapter (17662); sealing a chapter moves it on (`finish`, 17726).
- Chapter progress (which chapters are reached) is on its own key, apart from the run (CLAUDE.md v5.12).

### 9.3 Phase strings and `applyPhase`

`kit.setPhase(string)` is the only bookmark (8204; saved as `phase`, 11510-11531). CLAUDE.md's rule: saves run on
receipts, and "progress rides the phase string (the only receipt; an empty bag is not one)". The engine never reads
the string; the chapter does.

Chapter 4 (e4c4.js): phases `history`, `sight`, `bless`, `kept`, each followed by marks of what has been done
(`mark()` 5859-5868, `readMark` 5869-5874; `setPhase` 5880 writes `kit.setPhase(p + ':' + mark())`), for example
`bless:r,m,f,o,a,k,v,l1,l2,l3,w`. It is applied ONCE, on the first play frame (masters/v27.0/parts/d_play.js,
`updateNotes`: `if (!booted) { booted = true; applyPhase(kit ? kit.getPhase() : null); }`), by `applyPhase`
(7450-7459), which puts every person, prop and order where that phase has them.

### 9.4 How chapter 4 saved its fight, and what a Continue into it does

- **The fight's own progress is not saved at all**: not the blessing's share, not her health, not the wave, not the
  spirits. Only the phase (`bless`, with `w` once the water is his) and the stats.
- A Continue (`resumeRun`, main.js 16950-16998) rebuilds or refreshes the world, applies the saved stats and bag,
  puts the rig at `at` with `pitch.rotation.x = 0; camera.rotation.z = 0;` (16975-16982) and enters play under the
  card; the chapter's first frame then applies the phase. For `bless` with the water taken that runs
  `blessBegin(R, false)`: `giveWater(true); after(0.8, () => { if (live(run)) briefFight(); })` (6246-6249).
  **The fight starts again from its brief**, with the stats as they were at the last save.
- While the brief itself is open, a save is the run as it stood when the brief opened (`save0`).
- So chapter 4's answer to "a Continue in the middle of the fight" is: there is no middle. It is the simplest safe
  design and it is proven.
- What that leaves open: sanity already lost inside the fight was saved (the autosave ran during it), so a restarted
  fight begins poorer than the first try unless the chapter banks nothing until the end. Chapter 4's fight costs go
  through `kit.award(..., { minigame: true })` on the spot.

### 9.5 The receipts rule for awards

An award carries a note and pays only what is not already banked. Chapter 4's form (e4c4.js 5882-5886): `bank(note,
s, a)` looks for the note in `kit.getConduct().notes` and calls `kit.conduct` only if it is not there, so a phase
applied twice, a Continue or a replay cannot pay twice. A beat that spans a save is tagged as played in the phase's
marks. Spirit Vision is never saved: `kitReset` closes it (7942).

## 10 · Sound

### 10.1 A film's sounds: `sfx` and `STING_SAMPLE`

A film reaches sound only through `sfx(at, kind, vol)`. `kind` is a row of `STING_SAMPLE` (main.js 14896 onward: kind
to `[sample, level]`), played by `sting(kind, vol)` (15562-15630); a cue's volume MULTIPLIES its row. Cues must be
literal `sfx(t, 'name', ...)` calls, because the warm scan reads the film's text (`CUE_RE` 9967, `cuesOf` 9968,
`warmCues` 9977) and `chaptertest.mjs` (216-263) fails a kind with no row or a sample with no file. `STING_SYNTH`
(15526) names the few kinds the procedural fallback can fake; everything else is silent if its bytes have not decoded.
`sfxFade` (16084) fades one. A film ends at its last TRACK, so a cue after it never plays (chaptertest walks every
film against a stub, 404-519).

### 10.2 The buses, and the duck

- Voices go to the voice bus (`voiceBus`, main.js 10144: a boost of 3.5, a compressor, a limiter) or, for the cast,
  the voice stage (10135); `outFor(name)` (10427-10432) routes by which take set a name is in (`JAMES_TAKES`,
  `TEEN_TAKES`, `ADULT_TAKES`, `CAST_TAKES`, `WHISPER_TAKES`); anything else goes to the pack's gain.
- **Everything that is not a voice is ducked under any voice**: `const BG_DUCK = 0.40;   // -8 dB under any spoken
  line` (9635); `duckSync` (9653-9659) takes it down in 0.12 s and lets it up in 0.45 s.
- `kit.hush(k, { secs, hz })` (7888-7913) lays a low-pass over that same background bus; voices are untouched.

### 10.3 One-shots in play: `snd` and `worldSfx`

```js
function snd(name, vol = 1, rate = 1, pan = 0) {        // one-shot
  if (muted) return null;
  const buf = sndBuf(name);
  if (!buf || !actx || actx.state !== 'running') return null;
  const s = actx.createBufferSource();
  ...
  if (pan && actx.createStereoPanner) {   // where she IS, not just that she is
    const pn = actx.createStereoPanner();
    pn.pan.value = THREE.MathUtils.clamp(pan, -1, 1);
```

(main.js 10617-10639.) A chapter plays through `ctx.worldSfx` (8292), which is `snd` kept on a list so the engine can
stop every play-time one-shot when play is left (`stopWorldSfx`, 17772).

- **It returns null and plays nothing when the sound has not decoded.** No error.
- **There is no limit on how many play at once and no priority.** Each call is a new source.
- **There is no 3D listener.** Space is a stereo pan the caller computes (the engine's `ghostPan`, 10698-10702; the
  chapter's `panOf`, e4c4.js 6042) and a volume the caller computes by distance (chapter 4's spirit voices, e4c4.js
  6491-6498, which also allow at most two at once).

### 10.4 Beds

A chapter declares `ambience.beds: [[name, vol, pan, rate], ...]`. The ambient frame re-asserts every bed's volume
every frame (main.js 10885-10890), times a film's own duck (`duckOf`, 10829; set by `api.duck`, `duckLoop` 10825) and
the vision's. So a bed cannot be faded by calling `loopVol` (10642-10695) once; it is ducked through the film's
`duck`, or changed by the chapter's own multiplier where it has one. A loop left running at gain 0 still plays: a
chapter stops its loops when it is left (CLAUDE.md v14.16).

### 10.5 Warming, and packs

- A sound a play-time beat or a scene can ask for must be decoded BEFORE it is asked: `ctx.warmSounds([...])` (8314;
  `WARM_WANT` 8259, `packWarm` 10567, the engine's own set `warmPlaySet` 9930). Opening an event warms the event's
  sounds (5568-5570); a film from play warms its cues (8013).
- Which pack a sound travels in is COMPUTED by build.py (110-161): a sound is a chapter's when exactly one chapter
  quotes its name and the engine never does; otherwise it is shared, in every player's boot download. A name built by
  code at run time is not seen. An engine-owned sound for a new mode (a switch chime, a cooldown tick) would be
  shared by that rule, and episode 1's players would download it.

### 10.6 Voices, and the line queue

The engine's own narration (main.js 10717-10735):

```js
if (muted || narSrc || voiceSrc || state === 'cine'
    || liveVoices.size > 0 || voicePending) { sndBuf(name); return; }
```

**One voice at a time**: a line waits while any voice is live. A film's start stops every play-time line
(15886-15887). A chapter speaks through its own queue; chapter 4's (e4c4.js 8716-8744):

```js
function sayLine(name, vol = 1, onStart, pan) {
  if (dayClock.t < speak.until) return false;
  const start = () => { speak.voiceTo = dayClock.t + (SECS[name] || 2.5); speak.until = speak.voiceTo + 0.25; heard.add(name); if (onStart) onStart(); };
  if ((soundOff && soundOff()) || !worldSfx) { start(); return true; }
  if (worldSfx(name, vol, 1, pan)) { start(); return true; }
  speak.pending = { name, vol, start, pan, give: dayClock.t + 1.6 };
```

- A line is a BEAT, heard or not: muted, it is "spoken" silently for its own length, so whatever is chained on it
  still happens. Its length is `SECS[name]`; `chaptertest.mjs` (153-172) fails a chapter that speaks a line it has no
  `SECS` for, and every take needs its row in `src/voicelines.js` (271-361), with a master's title in full (276, 299).
- `queueLine`, `queueFn`, `queueGap` and `runQueue` (8733-8742) run lines one after another on the chapter's clock,
  which stands still under panels and menus; `line(name, who, onStart)` (8744) also plays the speaker's talking take.
- `sayLine` returns false when the floor is taken, and that refusal must not be ignored (CLAUDE.md v9.5).

### 10.7 What a fight with many overlapping effects must respect

1. Every instruction line ducks every effect by 8 dB for its whole length plus 0.45 s. "Many instructing voice lines"
   (his R4) and a loud fight pull against each other: the lines are short and queued, and nothing a player must HEAR
   to play (a telegraph, a cooldown coming back) may be an effect alone; it is on the screen too.
2. One voice at a time, for instructions, barks and both heroes. A line that would land late is dropped, not stacked
   (CLAUDE.md v5.30). Two heroes cannot talk over each other.
3. A cap on the chapter's side for repeated effects (fireballs, hits, spirits' cries), because `snd` has none.
4. Every sound warmed before the fight; every name quoted in the chapter so it rides the chapter's pack.
5. No gain over 1 (v23.1); effects levelled to the measured rules (v5.26, v10.4: a phone's speaker plays almost
   nothing under 120 Hz); a short rhythmic effect cut from 20 ms before its peak (v9.4).
6. Pan by the LENS (what is seen), the level by a stated rule (the hero's place or the lens's), written down.
7. A whisper or a breath goes round the voice bus (v6.9); a long chant is not a voice take (v24.0).
8. Loops stopped and one-shots let go when the fight is left, by any road: its end, a film, a loss, the menu's
   restart, a chapter change.

## 11 · The tests a new mode must pass or extend

`runtests.mjs` lists 24 harnesses and runs the picked ones two at a time; `testlib.mjs` serves `dist/` (so
`npm run build` first), and on this box needs `CHROMIUM_PATH=/opt/pw-browsers/chromium`. At most two browsers at once
(CLAUDE.md). Adding a chapter adds no harness.

### 11.1 The fixture: `src/chapters/chtest.js` and `fixturetest.mjs`

The fixture is a chapter of primitives that DECLARES every seam: `items: ['amulet']`, a `torch`, `render: {
phoneRatio: 1.9 }`, a `weapon` with no model (`{ item: 'rifle', rounds: 3, mags: 1, ... }`), `vision: {}`, hotspots
of every kind, a spirit, a target with `shootables` and `onShot`, a `groundAt` platform, and four films. `fixturetest.mjs`
(2,821 lines) boots `?ch=chtest`, fills a map `K` of named proofs, and fails if any is not exactly `true`.

One real proof, whole (fixturetest.mjs 515-524), the play lens's seam:

```js
K.lensSeam = await p.evaluate(async () => {
  const E = window.__enc;
  const frames = (n) => new Promise(r => { let k = 0; const f = () => (++k >= n ? r() : requestAnimationFrame(f)); requestAnimationFrame(f); });
  const a = E.lens();
  E.kit.lens(40, { secs: 0 }); await frames(3);
  const b = E.lens();
  E.kit.lens(null, { secs: 0 }); await frames(3);
  const c = E.lens();
  return a.took === false && a.fov === 72 && b.took === true && Math.abs(b.fov - 40) < 1e-6 && c.took === false && c.fov === 72;
}).catch(() => false);
```

Its form is the form every seam's proof takes: read the engine's own report (`E.lens()`) before; use the verb; read
again; give it back; read again; and assert that "before" and "after" are EXACTLY the world's own values. No fixed
waits: drawn frames are counted. Others to model on: `K.hushSeam` (538-551), `K.renderSeam` (556-561),
`K.visionSeam` (571-618), `K.ownSeam` (330-402, which declares a weapon over the fixture's through
`E.weaponDeclare`), and **`K.visionGoneWithChapter` (2777-2785)**, which deletes the declaration, calls
`E.kitReset()` and proves the seam is gone: the "absent means untouched" half of the law.

A third-person seam would owe at least: with no declaration, the camera's local position is exactly zero and the
frame's passes are the ones they were; declared and off, the same; on, the boom is where the declaration says, the
hands' pass is not drawn, the active body follows the pivot; a switch moves the pivot and nothing else; off again,
everything is exactly as before (the lens, the nod's clamp, the hands, the HUD's classes); a film started while it is
on sees no boom; `kitReset` clears it; and its save field round-trips and tolerates an old save without it.

### 11.3 `walktest.mjs`

Its list of chapters is written by hand: `KEYS` (line 39) ends `'e4c3', 'e4c4'`; **`e4c5` must be added**, and
chaptertest fails until it is. It floods the REAL collision grid at 0.06 m from the spawn and from every place in
`stage.arrivals`, and fails if a hotspot or the decision object cannot be reached, if the walkable ground leaves
`stage.keepIn` (which may be several `boxes`), if a ground height is not a number, if a load failed, or on any page
error. A later ground is walked where the chapter names it: `stage.grounds = [{ what, enter(), ready() }]`. **It
floods with the player's own `collide`**: it says nothing about a second body, a spirit, or a boom.

### 11.4 `leaktest.mjs`, `csptest.mjs`

- `leaktest.mjs` builds every chapter once, then runs 3 warm and 8 measured cycles of `rebuildStage` and fails if
  geometries or textures grow by more than 0.5 a cycle. Everything the mode makes (a boom's helper, a body's clones,
  pooled projectiles, a ring) must be disposed by the chapter's `dispose()` or by the engine's teardown.
- `csptest.mjs` serves the single-file build (`wrapped.html`, episode 1 only) under the strict no-blob, no-data
  policy. A hosted-only chapter is not in it, **but the engine is**: the seam's engine code must not make a blob: or
  data: URL or a worker from one.

In order: `node --check` on every chapter; `tools/probes/usebefore.mjs` (a name used before its declaration,
chapters and main.js); `tools/probes/undefscan.mjs` (undefined names in chapters, which are copied, not bundled);
`tools/probes/dupfuncs.mjs` (a function defined twice); `tools/patchthree.mjs`; esbuild; `build.py`, which asserts
that every sound reaches a pack (110-161), keeps the hosted-only lists (`E2_ONLY` 906, `HOSTED_ONLY` 960), refuses an
asset key that is also a sound's name (981), computes each chapter's assets (994) and checks the fonts (1083-1101);
then `wrap.py`. `src/chapters/e4/e4c5.js`, if it is generated from parts as chapters 2 to 4 of this episode are, is
scanned as the assembled file.

### 11.6 What the standing rules add for a mode like this

- "A new seam is opt-in and a bit-identical pass-through when absent, declared and proven (opt-in included) by the
  fixture, **shipped alone first when it is big**" (v12.0). This one is big.
- "For every engine change, say whether episode 1 can reach it ('unchanged by construction') and run episode 1 as
  the control" (v9.3).
- Probes drive the real input path: real pointer events and CDP touch with their own timestamps, on a touch context
  (v18.3, v14.5); a reaction is tested on a fake clock with a human's delay (v21.2).
- Saves are tested at every phase, by a Continue through the title on a phone, a same-sitting Continue, and every
  way into the chapter; a same-chapter replay is run twice and compared (v7.3, v8.2). A `?ch=` session cannot test
  any of it (main.js 11446).
- A phone picture with the HUD in it is taken at 390 x 844 CSS pixels, drawn at two device pixels or more (v25.5,
  v26.0), and on a low-resolution phone too (v26.1).
- Bodies are measured, not judged by eye: `tools/probes/jointscan.mjs`, `feetscan.mjs`, `clipscan.mjs`,
  `headturn.mjs`, `gait.mjs`, and a pose set beside a real photograph (v26.3). A hero seen from behind for a whole
  fight is a new view of both bodies.
- The frame's cost is measured on the real place: `tools/probes/drawn.mjs` (triangles and draw calls at the WebGL
  calls), `frameprof.mjs`, and a texture count that reads `__picsW`/`__picsH` (set at main.js 1499), because
  `gpumem.mjs` reads a freed picture as width 0 under `render.freePictures`.

## 12 · Risks and traps for a third-person two-character mode in THIS engine

Each with where it lives and a suggestion. The suggestions are for the designer to weigh, not decisions.

**12.1 A boom nobody else knows about.** `snapWorld`/`restoreWorld` keep the rig's place, heading, nod and roll only
(main.js 15802-15822); a Continue, a restart and the title reset the nod and the roll only (16982, 17857, 14676);
chapters' films place the lens by moving `yaw` (e4c4.js 7595-7601). A boom left on `camera.position` would offset
every film shot, the faint and the cards.
*Suggestion*: never store the boom as state a film can inherit. DERIVE it on the frame: the offset is non-zero only
while `state === 'play'` and the mode is on, and is written to exactly zero otherwise, every frame, by the engine.

**12.2 The aim starts behind him.** The shot's ray and the look-spots' cones start at the lens (main.js 4789,
3164-3168); the assist cone too (4695-4720). From 3 m behind a hero the ray meets whatever stands between, and the
reported distance is the lens's.
*Suggestion*: aim with the lens, fire from the hero. Take the aimed point (or the nearest spirit inside a cone, which
suits a thumb better than a reticle) and fly the ball from the staff's tip to it. Keep `stage.onShot`-style reports
so the chapter still decides what a hit means.

**12.3 The vision's eye is the lens.** The wave and `kit.wave` spread from `camera.matrixWorld` (src/vision.js 302).
With a boom, his sight opens from a point behind him; and the vision costs its passes (section 7.2) on top of the
fight. Every film closes the vision at once (main.js 15875).
*Suggestion*: if Spirit Vision is one of Master Zavier's abilities in the mode, make the eye a parameter of the pass
(a small, separately proven change to the vision's seam), and measure the pass on a phone before promising it. If the
spirits are simply visible in this fight, the vision's cost is not paid at all.

**12.4 His first-person arms over a third-person picture.** The hands' pass draws whenever anything under `handsRoot`
is visible (main.js 18279), and the end of every film from play forces `handsRoot.visible = true` (8033).
*Suggestion*: do not write `handsRoot.visible` from the mode (CLAUDE.md: "Never write a switch another owner owns").
Add the mode to the pass's own test, so the pass is skipped while it is on, and to the vision's `drawHands` (18250).

**12.5 The pivot bobs, tilts and has a neck.** The bob is written into `yaw.position.y` every frame (18044-18047);
the nod is clamped at plus or minus 1.2 radians (2051, 17995); the look is scaled by the lens (17977).
*Suggestion*: in the mode, no bob; its own nod limits (the way a pose sets `pitchLo`/`pitchHi`); the boom shortened
against the blockers and the floor so the lens never leaves the room (near plane 0.08 m, main.js 930), as a SMOOTH
function of the frame's clock (CLAUDE.md v25.5: a value solved every frame must not step).

**12.6 Collision is one point, for one body, and `keepIn` is not enforced.** `collide` tests a point at 1.0 m against
padded boxes and reads `yaw.position` (main.js 17928-17934); `stage.keepIn` is walktest's only. The second hero, the
spirits and the projectiles have no test at all; chapter 4's spirits pass through everything (e4c4.js 6568-6607).
*Suggestion*: the engine offers the same test for any point ("would this body be stopped here"), used for the idle
hero and anything else that must not cross a wall; the arena's edge is BLOCKERS (CLAUDE.md v25.5: a way out is proved
shut by the flood, and a filmed set has no solid walls until they are made solid), with `stage.keepIn` declared so
walktest holds it.

**12.7 A switch is a teleport of the rig.** The ground snaps past 1.5 m and eases under it (17923); the velocity is a
module variable and carries over (18037); the save's `at`, every distance in section 3.1 and the chapter's "me" jump
with it. If the idle hero is made solid (chapter 4's `castSolid`, e4c4.js 5947-5951), the rig can land INSIDE his
padded box and be stuck (CLAUDE.md v5.03: the spawn stays clear of padded blockers).
*Suggestion*: one engine verb does the whole switch in one frame, in a fixed order: drop the incoming hero's blocker,
move the rig, zero the velocity, raise the outgoing hero's blocker where he stands, set the heading. Show it as a cut
with its own short picture and sound, never a camera flying through the room (v25.5: a cut changes what is looked
at). Refuse it, with words, when it cannot be done (mid-cast, mid-film).

**12.8 A Continue lands in the middle of a fight that has no middle.** The autosave runs every 8 s in play
(11499-11508); only the phase string, the stats and the bag are kept; chapter 4 restarts its fight from the brief
(e4c4.js 6246-6249). A Continue puts the rig at `at`, nod zero, in FIRST person (16975-16982), before the chapter's
first frame applies the phase.
*Suggestion*: take chapter 4's answer: the fight is one phase, a Continue restarts it from its brief under the
curtain, and nothing is banked until it ends (so a restart is not poorer than the first try). If anything of it must
be saved, it is a small validated field like `weapon` (11529, 11555-11558), and old saves without it must still load.
Test by the real Continue, not `?ch=` (11446).

**12.9 A replay never re-runs `build()`.** `kitReset` (7914-7948) and the chapter's `reset()` must put back
everything the mode changed: the boom, the active hero, both bodies' places and takes, cooldowns, lives, pooled
projectiles, seeded streams, body classes, the nod's limits, the lens.
*Suggestion*: the engine's part is cleared in `kitReset` beside the weapon's and the vision's lines (7940-7942), and
the fixture proves it; the chapter's part is listed in its plan as "what reset forgets" and read object by object
against a fresh start (the method of `tools/probes/e4c3replay.mjs`).

**12.10 The phone is already full.** Chapter 4's fight is 0.64 to 1.40 million triangles and about 1.0 GB of pictures
(section 7.4). Pho has ONE level: 168,029 triangles and 231 bones wherever he stands, and a 4096 sheet; the only
lighter Pho is the 21,989-triangle far level (`assets/phof.glb`). A hero's level is chosen by distance from the LENS
(e4c4.js 3475-3486): a boom shortened against a wall to under 2.2 m would swap a hero to his full body mid-fight.
*Suggestion*: pin both heroes' levels for the whole mode (`P.force`); decide by measure whether Pho needs a middle
level for this segment; make the spirits no heavier than `p4wander`; price the place first (`tools/probes/drawn.mjs`
on the real room) and state the numbers in the plan, as CLAUDE.md v24.3 asks ("State the cost of a change, measured
not guessed").

**12.11 A new material on screen is a stutter, and a new light is worse.** Shaders are compiled under the curtain
(`warmWorld`, main.js 16578; the curtain's rule, CLAUDE.md v14.15); a lit material's shader depends on the count of
lights (`lightCounts`, 16394; v15.1).
*Suggestion*: every fireball, ring and particle material exists from `build()`, hidden, so it is warmed; pooled, never
made in the fight; unlit and painted, no PointLight on a ball. For colour over a bright surface, normal-blend the hue
and add the glow as its own layer (v8.8); a flat card of light among bodies is drawn with `depthTest` off (v25.5).
Gold is Grandmaster Pho's alone (v25.5), which the shockwave's colour must respect.

**12.12 One voice, and an 8 dB duck.** Section 10.7. His R4 asks for many instructing lines.
*Suggestion*: instructions as short queued lines with their words on screen (`kit.captions`, or the objective line),
each tied to the first time a thing is needed; everything needed to play is also drawn (a cooldown ring, a telegraph).

**12.13 Touch has two fingers' worth of input and a 390-point screen.** The left 45 % is the stick, the rest the look
(main.js 9359-9370); buttons are page elements above the canvas at fixed places (section 2.3); there is no gesture
beyond a tap. A switch, two or three abilities for each hero, their cooldowns, two lives and a progress bar must fit
beside the mute, menu and bag column and above the interact prompt.
*Suggestion*: one cluster at the bottom right in the weapon HUD's place (it already pushes the prompt up: shell.html
466-474), buttons on `pointerdown` with `stopPropagation` as FIRE is (7120), the same buttons re-labelled by hero
rather than two sets, cooldowns as the strain ring's kind of ring (shell.html 3273). Then the bounding-box pass at
390 x 844 and on a desktop (section 2.7), by hand, because no harness does it.

**12.14 Desktop keys are nearly used up.** W A S D, the arrows, Shift, E, F, V, Q, R, Space, Esc, I, M are taken
(main.js 9215-9225, 14283, 14828). A locked click fires the weapon and a right click aims (9304-9306).
*Suggestion*: Tab or a digit for the switch, digits or the mouse buttons for abilities; key labels shown only to a
fine pointer (v18.5). A brief names the input for each device.

**12.15 A portrait phone sees a third of the width.** 72 degrees is vertical (main.js 929); at 390 x 844 that is
about 37 degrees across. From behind a hero, spirits to either side are off the screen.
*Suggestion*: decide the phone's lens and boom for the mode on the phone first (`kit.lens`; a cramped interior gets a
wider lens on a phone, v24.21), and mark what is off screen (the waypoint's arrow, 3642-3660, is the existing form).
Every shot and screen must work on both framings (v21.19).

**12.16 The walk's speed does not match any take.** The rig walks at 2.55 m/s, 4.46 with Shift (18034-18035), on a
clamped frame time (17960). Chapter 3's walker ties a take's rate to the ground covered and clamps it at 0.5 to 1.35
of the take's pace, about 1.25 m/s (e4c3.js 7265-7271). Driven at 2.55 m/s a walking take slides or sprints.
*Suggestion*: the mode sets each hero's own speed from his takes (measured: `tools/probes/gait.mjs`), walks him on
wall time, and drives the take's rate from the ground actually covered (v7.1). A phone has no Shift: there is one
speed, or a stick pushed fully is the run.

**12.17 Pho's moving takes are unproven, and there are only forward ones.** His `Walking` (1.03 s) and `Running`
(0.63 s) are played by neither chapter that casts him (section 6.6); `Running` is not in the list of takes whose travel is
taken out (`WALKS`, e4c4.js 1741), so whether it moves his hips over the ground is not known here; his robe was
fitted take by take, and chapter 4 keeps per-take rules for his standing takes (`PHO_STAND_SHOULDERS`, e4c4.js
5492-5493). There is no strafe, no backward step and no turn in place in his file.
*Suggestion*: before the design leans on any take, measure it as a motion on his body and photograph it from behind,
full size (v25.5, v26.3). The hero turns to face his travel, so only forward takes are needed. Which casts are the
fireball and the shockwave is chosen from pictures of every cast seen from the boom's side.

**12.18 A body's culling sphere is 1.9 m round its waist.** `ctx.cullBySphere(P.group, 0, 0.9, 0, 1.9)` (e4c4.js
2120), with every skin's own culling off. A staff held out, a lunge or a leap can leave it and the hero vanishes at
the screen's edge.
*Suggestion*: the heroes' spheres cover every pose of every take they play with the staff in hand (v8.4).

**12.19 The static take check does not see `mkPerson`.** Section 11.2. A wrong take name on the new Zavier rig is a
bind pose and a console warning.
*Suggestion*: extend chaptertest to read the names `mkPerson`, `take` and `pose` are given and check them against the
file's clips; until then, a probe that counts console warnings on every take the mode can play.

**12.20 Clocks.** The chapter's clock stands still under panels and menus while wall time and voices run on (v21.21);
every clock in play runs on wall time, not the clamped frame time (v7.1); time with the tab hidden is never play
(v21.23); nothing charges or faints him under a panel he is reading (v11.4). Chapter 4's tick stops outside play
(e4c4.js 6570).
*Suggestion*: cooldowns, spirits and the ring run on the chapter's fight clock, gated on `getState() === 'play'`,
and stop under every window; nothing in the fight is timed by frames.

**12.21 The ring that is drawn and the ring that is tested.** `kit.wave` is a picture only, from the lens, one at a
time, and needs the vision declared (main.js 4004-4027).
*Suggestion*: the gameplay ring is a mesh whose radius is one function of the fight's clock, and a spirit is struck
when that same function passes its distance from the ring's centre ("What is drawn and what is tested are the same
number or the same function", v8.7). `kit.wave` may dress it only if 12.3's eye parameter exists.

**12.22 It must be seen, and it must be fair.** "A beat that matters is guaranteed to be seen, never left to chance"
(v21.17); "A minigame must test the lesson, not the player's eyesight, memory or touch latency" (v24.12); "Every
timed phase has a failure state that ends it; nothing soft-locks" (v7.4); "Whatever state the chapter obeys is on
screen" and "a lock always says why" (v8.1); "No line, hint ... lies" (v14.2).
*Suggestion*: the shockwave's first use is taught and guaranteed (a prompt that waits, or a film), aim is assisted, a
cooldown is drawn and a press on it says why not, and the fight ends by its own clock whatever the player does.

**12.23 Rules this mode lifts or leans on, to be said out loud in the plan.** The grown Master Zavier is never seen
(v24.56) is lifted by his R3 and R5; no rigged model of him is in the build yet (sections 6.6 and 6.7). The equipment panel's figure is
keyed to the episode (`ZAV_FIGURE`). Episode 1 must be unchanged by construction. The seam ships alone first.

**12.24 What the mode borrows from first person must be given back.** A film from play takes the hands, the lens and
the vision back at its start and forces the hands on at its end (15865-15878, 8033); the red edge, the chill, the
pulse and the hurt frame are play's and are drawn over whatever the picture is; a faint is a first-person film
(17618-17632) and `lose()` rewrites the save (17662).
*Suggestion*: the mode is left before any film, card or faint begins (the engine's film start is the one place every
film passes: 15856), and entered again only by the chapter, in play.

## Appendix · How this was measured, and what is not known

**The frame counts** (section 7.4): one headless Chromium, one page, `dist/` of v27.0 over testlib's server, a touch
context of 390 x 844 at device ratio 1, `?ch=e4c4`, Start, the film skipped; the WebGL draw calls wrapped to count

**The models' figures**: read from the files' own JSON (triangles, joints, takes) and with gltf-transform (pictures).

  from behind. None was played for this survey.

- No harness was run for this survey; the tests are described from their source.
