## 1 · THE LABEL — a comment that was never a test

`src/main.js`, in the play frame, under a comment that has read the same
since v2.1:

```js
// the heap: one prompt at a time, and only when it is actually on screen —
// a key prompt for something behind you is noise
const reach = stage.pile.dist() < stage.pile.radius && stage.pile.inView();
...
if (d < 6.2) ui.prompt.classList.remove('hide'); else ui.prompt.classList.add('hide');
```

The comment says on screen. The code says within 6.2 metres. **Only `reach`
ever consulted `inView()`, and `&&` short-circuits, so on any frame the player
was out of arm's reach the visibility test was not even evaluated.**

Why it survived eleven major versions: in episode 1 the decision object is
across a void deck, a room or a flat, so distance and visibility almost always
agree and the label reads as a nudge you can walk away from. Episode 2 put the
decision object where the player already stands — his own bed, the ground
under his feet, a man across the hall he has not earned the right to talk to
yet — and the label became permanent furniture in three chapters at once.

**The fix is one call, and no new seam.** `inView()` is already the one
function that knows, and each chapter's is already the right answer:

| chapter | `pileInView()` | what it means for the label |
|---|---|---|
| ch1–ch5 | projects inside the viewport | shows only while the object is on screen |
| e2c1 | `bedWants() !== BED_NOTHING` + near/on-screen | gone through the night, when the bed offers nothing |
| e2c2 | `phase === 'encik'` | gone across breakfast |
| e2c3 | `phase === 'decide'` | gone through the torch sweep |
| e2c4 | `phase === 'decide'` | gone through the serials |

So the frame computes it once and shares it with `reach`:

```js
const onScreen = stage.pile.inView();
const reach = stage.pile.dist() < stage.pile.radius && onScreen;
...
if (d < 6.2 && onScreen) ...
```

A first pass added an optional `stage.pile.ready()` and declared it in all four
episode-2 chapters. It was **reverted before shipping**: every one of those
chapters already folds liveness into `inView()`, so the seam bought nothing and
would have rotted. A seam that is redundant on the day it ships is a seam that
will drift.

## 2 · THE TREE — mine, from the day before

> the 1/6 screenshot of looking at the tree cannot be clicked

v12.3 added one line to `nearestHotspot()`:

```js
if (h.dwell > 0) continue;
```

…which took every look-spot off the interact badge. The reasoning in that
comment was about a real defect — a press used to fire whichever spot was
NEAREST, so a tap while looking at a tree twelve metres off answered the
ground at the player's feet, out of order — but the defect was the ORDERING,
not the press.

**What made it fatal is the touch path.** A tap on a phone runs
`onTouchEnd` → `stage.pile.hits()` and nothing else; the only route a hotspot
has to a finger is the badge's own click handler. So removing the badge
removed the whole interaction on the only device Chad plays on, while desktop
kept working through E. That is why it read as "cannot be clicked" rather than
"is hard to hit".

The fix keeps v12.3's intent and restores the input:

```js
if (h.dwell > 0 && !hotspotAimed(h)) continue;
```

`hotspotAimed()` is the aim test lifted out of `dwellHotspots()` so the dwell
that GRADES the look and the badge that OFFERS the press cannot disagree about
what the player is looking at. A press can now only ever fire the exact spot
the look was already about to.

### The cone was a quarter of the beam aiming it

Chapter 3's torch declares `angle: 0.40` — the spotlight's half-angle. The
torch spots asked for `aim: 0.11`. A tree could be lit square in the middle of
the light and count for nothing, which from the player's side is "it doesn't
work". Widened to about half the beam:

| spot | was | now |
|---|---|---|
| fig, log, gap, chem | 0.11 | 0.20 |
| buddy, kneel | 0.12 | 0.22 |
| feet | 0.14 | 0.28 |

Bounded by the anchors' own separation, computed from the scrape at eye height
1.62: the closest two of the seven are the trees at **47°**, against the 23°
two 0.20 cones would need to touch. No look can answer two spots.

Measured on the shipped build:

```
fig, 0.15 rad (8.6°) off centre : dwellT 0.54 → fires   (dead before this release)
log, aimed, then pressed        : FIRED
gap, 0.34 rad (19°) off centre  : dwellT 0.00           (the cone did not go slack)
```

### The marker stops lying

Every hotspot mark wore the same `!`, which on a phone is an instruction to
tap. A look-spot's mark is a round eye now (drawn in CSS, so no font has to
carry a glyph) and an arc around it **fills with the spot's own `dwellT`** —
the one number the grading uses, so what is drawn and what fires cannot drift
apart. The v8.7/v8.8 `ZONE_R` rule, applied to a reticle instead of a floor.

## 3 · THREE MORE IN CHAPTER 3, all from v11.3, all mine

**A guard naming two phases that do not exist.**

```js
if (phase === 'press' || phase === 'down') { bushAt = 0; callAt = 0; return; }
```

The chapter's phases are `gear`, `look`, `pressure`, `decide`. The guard never
fired once. So for three releases the bushes rustled and the night animals
called straight through the beat the chapter is built on — under
*"Nothing around... no one... no footsteps... not even the sound of vegetation
moving around me."* Now `phase === 'pressure' || phase === 'decide'`.

**The far ghost runs had no guard at all** — and they carry `ghostrunleaf`,
vegetation moving, by name. Same guard; an in-flight run is ended on the frame
the pressure begins.

**`reset()` never cleared the accumulated look**, so a replay opened with
credit banked from the run before. e2c4 has cleared it since v12.3; e2c3,
where the seam was written, never did. Visible now that the mark draws it — a
replay would have opened on a half-filled ring.

and `activeSpot` has three readers, all of which accept a look-spot.
